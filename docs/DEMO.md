## 二、2 分钟分镜（照着念就行）

**0:00–0:15 ｜ 开场：一个问题**
画面：页面上那只输入框。
旁白：
> 「后台的筛选条件经常有十几个，业务同学不会用，每次都要找开发。
> 这个 demo 就做一件事：让他们用一句话查。」

**0:15–0:45 ｜ 主路径：一句话 → 条件 → 表格**
操作：点示例 chip「上个月华东区退款超过 500 的订单」。
画面：条件一个字一个字长出来 → chip 出现 → 表格填充。
旁白：
> 「点一下，模型把这句话翻译成三个条件：地区等于华东、状态已退款、金额大于 500，时间自动换算成上个月。
> 注意这里是**流式**的，前半句就已经能看到它在写什么。」
停 1 秒，指一下「条件回显」区：
> 「这一块是整个项目的核心：模型理解成了什么，直接摊给用户看。理解错了，用户当场就能发现、重新问。」

**0:45–1:05 ｜ 图表**
操作：点右上角「图表」→ 再点「按月」。
旁白：
> 「同一批数据，一键切成图表。按分类给柱状、按时间给折线，自动选。
> 图表的统计口径和表格**完全一致**——都受那个「最多返回 50 条」约束，不会出现表格 50 条、图表 2494 条这种假数据。」

**1:05–1:25 ｜ 多轮追问**
操作：输入「只看华南的」→ 回车；再输入「再按月份拆一下」。
旁白：
> 「可以接着追问。只说『只看华南的』，它保留了上个月的退款条件，只改了地区。
> 再说『按月份拆一下』，筛选条件一个字没动，只是把展示方式切成按月——为此我在条件结构里加了一个专门的字段。」

**1:25–1:45 ｜ 异常也能兜住**
操作：输入「帮我看看最近的情况」。
画面：橙色面板「这句话我没能转成查询条件」+ 结果区不铺全量表，只给一个「仍然查看全部订单」。
旁白：
> 「这句是故意问模糊的。以前它会返回全部 5000 条——看着像成功了，其实什么都没回答。
> 现在它会明说没看懂，并且**不**默认查全量。」

**1:45–2:00 ｜ 收尾**
画面：滚到页脚，或切到 README 截图。
旁白：
> 「技术上最关键的一条：模型只输出 JSON 查询条件，不生成 SQL。字段有白名单，枚举有校验，模型编字段会被拦下来，再退到本地规则兜底。
> 所以它最坏的情况也只是查错数据，不会变成一次注入。」

## 三、3 分钟面试话术

按「痛点 → 方案 → 难点 → 结果 → 反思」讲，最后一点最值钱。

1. **痛点**：中后台的筛选条件十几个，业务人员不会用，每次都要找开发改。
2. **方案**：自然语言 → **JSON 查询条件**（不是 SQL）→ 白名单校验 → 引擎解释执行。
3. **难点**（挑两个讲）：
   - 模型输出不稳定：Schema 约束 + 字段/枚举白名单 + 校验失败自动规则兜底；10 句测试集 10/10。
   - 体验：SSE 流式，首字 0.3–0.9s；可取消，取消时同时掐断上游请求（省 token）。
4. **结果**：原本 6 次点击的筛选，变成一句话；点查询到出结果 0.6–1.3s。
5. **反思**：**什么不该用 AI** —— 精确报表、合规查询、涉及金额的写操作，必须走表单；AI 只做「查询入口」。

## 五、预判追问

**Q：为什么不让模型直接生成 SQL？**
A：两个原因。注入——模型可能拼出 `DROP`/子查询；幻觉——它会把不存在的字段写进 SQL，报错还是轻的，静默查错数据更糟。JSON 条件可以逐字段校验，最坏只是查错数据。

**Q：模型输出不稳定怎么办？**
A：三层。① prompt 里写死字段和枚举；② 出口做 Schema 校验，非法字段/枚举直接拒绝；③ 拒绝后不报错，退到本地规则解析，用户照样拿到结果。另外每天跑一次 10 句回归集。

**Q：首字 0.3–0.9s 怎么做到的？**
A：SSE 流式。模型一边生成一边推，前端逐字渲染，不用等整个 JSON 完。实测首字 0.47–0.86s，整段 0.6–1.3s。

**Q：为什么最后部署在 EdgeOne 而不是 Vercel？**
A：Vercel 构建部署都正常，但 `*.vercel.app` 在国内被 DNS 污染（解析到 Facebook 的 IP 段），直连边缘 IP 也被重置。能部署 ≠ 能访问，所以换成国内可达的平台。顺带把云函数对文件系统的依赖也去掉了——数据编译成模块内联，换平台只换适配层。

**Q：这种方案的成本和边界？**
A：单次解析约 ¥0.0015，5000 条数据全程内存过滤，无数据库。边界是不能做聚合式提问（「按渠道统计」会明确说无法解析），也不该用于写操作。
